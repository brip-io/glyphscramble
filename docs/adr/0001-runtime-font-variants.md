# ADR 0001: Generate one-use response variants ahead of demand

- Status: Accepted
- Date: 2026-09-03
- Issue: [R01](../design/R01-runtime-font-generation.md)

## Context

The original request path reconstructed `cmap` and ran the full Google WOFF2
encoder after a browser requested a tokenized font. The promise returned by
`woff2-encoder` did not move its WASM work off Node's event loop. A local
measurement of the pinned Inter Latin variable fixture (122,912 normalized
bytes) took 454 ms cold and about 309 ms warm on Node 26. Earlier review
measurements covered 182-877 KB normalized faces and took 681-2,075 ms. The
existing CLI measured only text encoding, so it did not expose this cost.

The runtime must preserve a fresh mapping per protected response while placing
hard bounds on work, memory, and failure behavior.

## Options considered

### One-use pre-generation pool

Generate complete response variants before demand, consume each variant on a
context's first protected operation, and retain it only until its encrypted token expires. This makes
the document and font request paths independent of compression latency. It
introduces process state, startup work, and an explicit overload condition when
demand outruns refill capacity.

### Worker-thread compression on cache miss

Moving compression to a worker protects the event loop, but the browser still
waits hundreds of milliseconds or seconds for a cold font. It also performs one
full compression for every token on the request path. Worker isolation is useful
as the pool's generation mechanism, not sufficient as the request architecture.

### Prepared coverage subsets

Smaller source faces reduce every generation cost and remain strongly
recommended. Glyph closure for GSUB, GPOS, variation, and color tables makes
physical subsetting a separate correctness project. R04 coverage currently
limits the permutation and `cmap`; it does not remove outlines. R01 therefore
must not claim that configured coverage physically subsets a face.

### Time-window rotation

A shared mapping per time window reduces state and generation volume, but it is
reusable across responses and weakens the primary claim. It is rejected for the
v0.1 runtime. A future provider may add it only as a separately named mode in
configuration and payload metadata.

### Alternate native/WASM encoders

Both the pinned encoder and `woff2-encode-wasm` wrap Google's reference WOFF2
implementation and produced essentially the same 309 ms warm result for the
fixture. A native addon could improve throughput, but it adds platform binaries
and supply-chain/release complexity. The provider boundary permits a future
encoder without changing tokens or framework adapters.

## Decision

Use a bounded one-use response pool as the only production runtime mode in
v0.1.

1. Engine startup prepares a configurable low watermark before returning.
2. Refill work patches `cmap` outside a request handler and performs WOFF2 WASM
   compression in worker threads.
3. A response context consumes one ready variant lazily on its first
   `scramble()` call or token read; an unprotected context consumes nothing.
   Pool exhaustion throws before plaintext can be emitted.
4. The encrypted token carries a random variant id, its random seed, expiry, and
   the explicit `response-pool` mode.
5. A variant is never assigned to a second response. Repeated GET/HEAD requests
   for the same valid token read the already-generated bytes and start no job.
6. Ready and issued variants share one byte ceiling. Ready variants and issued
   tokens both expire; valid issued variants are never evicted to make room.
7. Generation has explicit concurrency, queue, timeout, cancellation, and
   capacity limits. Every overload or missing-state path fails closed.
8. Metrics expose counts, queue/cache gauges, and bounded timing percentiles.
   They never contain text, seeds, tokens, mappings, or variant ids.

The defaults are a low watermark of 2, high watermark of 4, two concurrent
generators, 64 queued face jobs, a 10-second per-face timeout, and a 64 MiB
combined cache. Unused ready variants remain random and bounded by the high
watermark; issued variants expire with their tokens.

## Performance gates

`glyphscramble benchmark` now measures preparation, pool startup, permutation,
10,000-scalar encoding, token validation, pool lookup, response construction,
and WOFF2 generation. It reports p50/p95/p99 instead of a single encoding p95.
CI uses the pinned OFL Inter variable face at 122,912 normalized bytes and the
same real face padded with an inert, incompressible table to exercise the 1 MiB
resource path. Three cold five-variant engine starts measure real WOFF2 worker
throughput. The first batch is labelled process-cold and is governed by the
whole-pool startup ceiling; the next two are labelled process-warm and are
governed by the per-generation p95 ceiling. This prevents one-time worker/WASM
startup from being counted against both gates while keeping every measurement
visible. Fifty response acquisitions and prepared-font lookups then exercise
the production pool and engine with prebuilt byte payloads, keeping the 5 ms
and 10 ms request-path gates meaningful instead of treating the slowest of only
five shared-runner observations as a percentile. R12 still owns a naturally
large real-font matrix.

For R01, a prepared font response must remain below 5 ms p95 and a complete
10,000-scalar response acquisition below 10 ms p95 on Node 22 and 24. CI
regression ceilings are 2,000 ms p95 around 100 KB and 5,000 ms p95 around 1 MB;
the five-variant reference pool must start below 4 seconds and 12 seconds
respectively. These deliberately include shared-runner variance: the benchmark
publishes the exact measurements, while R12 establishes release-grade targets
on controlled hardware and real large-font fixtures.

These operational ceilings do not erase the parent plan's more ambitious 50 ms
and 200 ms transformation goals. The current Google WOFF2 codec does not meet
those goals; R12 must either qualify a faster encoder/prepared subset strategy
or keep that release gate explicitly open. Request latency is not reported as
compression latency.

## Consequences

- A process restart invalidates still-live font tokens because variant bytes are
  deliberately not reconstructible on the request path. The endpoint returns
  `410` and the client guard keeps the protected block hidden.
- Capacity planning depends on generated face size, token TTL, response rate,
  and the number of configured faces. Increasing the TTL without increasing the
  byte budget can exhaust the ready pool.
- Serverless environments that cannot retain process state are unsupported by
  the response-pool mode. They must not silently switch to per-window rotation.
- Pre-subset source fonts remain the most effective way to reduce startup CPU,
  memory, and refill time while physical subsetting is not implemented.
