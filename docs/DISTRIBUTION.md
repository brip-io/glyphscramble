# Distribution and releases

npm is GlyphScramble's only package registry. GitHub Releases are the source
and evidence channel, and version-pinned CDNs expose only the small browser
payload loader. BRIP does not mirror releases to JSR or GitHub Packages.

## Install

The initializer is the shortest supported path and installs the detected
adapter. It requires Node 22 or 24 and never contacts BRIP:

```bash
npx @brip/glyphscramble init
pnpm dlx @brip/glyphscramble init
yarn dlx @brip/glyphscramble init
bunx @brip/glyphscramble init
```

For manual installation, use the core package plus one server adapter. UI-only
packages are already dependencies of their server adapters:

```bash
npm install @brip/glyphscramble @brip/glyphscramble-next
pnpm add @brip/glyphscramble @brip/glyphscramble-nuxt
yarn add @brip/glyphscramble @brip/glyphscramble-sveltekit
bun add @brip/glyphscramble @brip/glyphscramble-astro
```

Vite static builds use `@brip/glyphscramble-vite`; generic Fetch/Node servers
use the core package directly. See the [framework matrix](FRAMEWORKS.md).

## npm and GitHub channels

All nine public packages use one compatible release version. Prereleases keep
their suffix and publish only to npm's `beta` dist-tag; they must never move
`latest`. Stable releases alone publish to `latest`. Changesets is kept in
`beta` prerelease mode until the stable-release review explicitly exits it.

Each npm release corresponds to an exact signed `v<version>` Git tag and an
immutable GitHub Release. The release workflow packs the same artifacts it
publishes, rejects source maps, fixtures, local dependency paths, unexpected
executables, and incomplete package metadata, then attaches:

- `package-inventory.json`, with every package archive and SHA-256;
- `checksums.txt` for direct verification;
- `sbom.spdx.json` describing the release packages; and
- source archives generated by GitHub.

Final public qualification adds the qualification-manifest digest to the
inventory. A `null` value means the release is a rehearsal and cannot satisfy
the public-release gate.

Publication uses [npm trusted publishing](https://docs.npmjs.com/trusted-publishers/)
from `.github/workflows/release.yml`: GitHub's `npm` environment, a GitHub-hosted
runner, Node 24, npm 11, and `id-token: write`. The npm trusted-publisher entry
for each package must name `brip-io/glyphscramble`, workflow `release.yml`, and
environment `npm`. No `NPM_TOKEN` is accepted by the workflow. npm attaches
provenance for the public packages, and the post-publication job re-downloads
every archive, compares SHA-256, checks provenance, and verifies dist-tags and
GitHub evidence.

## Browser loader CDN

The core build emits `dist/browser.sri.json` beside one self-contained ESM
loader. For `0.1.0-beta.0`, the exact immutable URLs are:

```text
https://cdn.jsdelivr.net/npm/@brip/glyphscramble@0.1.0-beta.0/dist/browser.js
https://unpkg.com/@brip/glyphscramble@0.1.0-beta.0/dist/browser.js
```

```html
<script
  type="module"
  src="https://cdn.jsdelivr.net/npm/@brip/glyphscramble@0.1.0-beta.0/dist/browser.js"
  integrity="sha384-ToDz5tOdlYuY4UYKznb+q06ff0idIFj79e/yKzdxyoo4mLY8/EBhOfW0ATe6eSr3"
  crossorigin="anonymous"
></script>
```

The integrity value is generated from the packed bytes and verified during
release. Never use an unversioned or `latest` CDN URL. The loader only reveals
an already-issued `GlyphPayload`; it cannot scramble plaintext, create a font,
or replace a server adapter/static compiler.

## Rollback and deprecation

npm package versions and Git tags are immutable. Never delete and recreate a
release or replace archive bytes. For a bad release:

1. stop deployment and record the affected package/version;
2. publish a fixed patch through the normal signed-tag workflow;
3. move `beta` or `latest` only to the verified replacement; and
4. deprecate each affected package version with a specific repair message:

```bash
npm deprecate '@brip/glyphscramble@0.1.0-beta.1' \
  'Use 0.1.0-beta.2: beta.1 has <specific defect>.'
```

Deprecation is an operator action requiring npm owner approval. It does not
alter existing installs. If credentials or package ownership may be involved,
follow [SECURITY.md](../SECURITY.md) before publishing a replacement.
